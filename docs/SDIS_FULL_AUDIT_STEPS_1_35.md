## 5. High findings

### AUD-01 — Order lifecycle transitions enforce no RBAC permission (Steps 27/11)

- **Severity:** HIGH · **Blocks completion:** YES
- **Files:** `src/app/laboratory/order-service.ts:245–293` (`transitionOrder`), `:380–399` (`cancelOrder`); exposed at `src/transport/router.ts:415–439` (`POST /api/v1/diagnostic-orders/{orderId}/transitions`)
- **Problem:** `transitionOrder` asserts a permission **only** when `to === 'VERIFIED'` — and then the wrong one (`SETUP_MANAGE`, see AUD-02). Every other transition (`ACQUIRED`, `PROCESSING`, `RESULT_ENTERED`, `FINALIZED`, `REPORTED`, `CANCELLED`) requires only `requireSession`. `cancelOrder` delegates to `transitionOrder` with no gate of its own. Any authenticated session — including the read-only **viewer** tier — can therefore advance, finalize, report, or cancel any in-scope diagnostic order.
- **Evidence:**
  - `order-service.ts:252–258` — the sole `assertPermission` in `transitionOrder`, guarded by `if (to === 'VERIFIED')`.
  - `order-service.ts:380–399` — `cancelOrder` → `this.transitionOrder(...)` with no permission assertion (compare `specimen-service.ts:201`, where `transitionSpecimen` asserts `SPECIMEN_CREATE`).
  - Router `transitions` branch (router.ts:425–437) calls `transitionOrder` directly after `requireResolvedSession` only.
  - Test gap: `tests/transport/laboratory-lifecycle-http.test.ts:171` asserts only `unauthenticated transition is 401`; **no test asserts a viewer 403 on order transitions** (specimen, report-finalize, and notification lifecycles all have tier tests).
- **Why it matters:** the diagnostic lifecycle (result entry → finalization → reporting → cancellation) is the clinical core. An operator- or viewer-tier credential — or any compromised low-privilege token — can finalize unreviewed content, report it, or cancel active orders, while the audit trail records it as legitimate. This contradicts the documented "fail-closed AuthorizationService wired into every capability service" (`FOUNDATION_GATE.md` §3) and the RBAC matrix intent (`order.create` = operator tier).
- **Reproduction:** authenticate as viewer; `POST /api/v1/diagnostic-orders/{id}/transitions {"to":"FINALIZED","at":"…"}` on an in-scope VERIFIED order → 200 (expected 403). Unit-level: call `transitionOrder` with a viewer session → succeeds.
- **Recommended fix:** assert `PERMISSIONS.ORDER_CREATE` (operator tier) at the top of `transitionOrder` (keeping the additional manager-tier gate for `VERIFIED`), and add viewer-403 HTTP + service tests for every transition target. Do not weaken the VERIFIED gate while renaming it (see AUD-02).

## 6. Medium findings

### CON-01 — Concurrent distinct-key stock depletions can drive the ledger negative (Steps 31/14/33)

- **Severity:** MEDIUM · **Blocks completion:** YES (for the "negative stock impossible" claim)
- **File:** `src/infrastructure/database/inventory-repository.ts:272–309` (`applyDepletingMovement`)
- **Problem:** the "atomic" floor is `INSERT … SELECT … WHERE (SELECT SUM…) >= $qty` under default READ COMMITTED. The aggregate subquery takes **no row locks**, so two concurrent `issueStock` calls with **different** idempotency keys can both evaluate the predicate against the same snapshot and both insert — write-skew → negative derived balance. The per-key advisory lock (`withExclusive`) serializes same-key replays only. The code comment ("row-level locking on the aggregate subquery's rows serializes the two INSERTs") is inaccurate: plain SELECT subqueries do not lock.
- **Evidence:** implementation quoted above; `inventory-service.ts:578–595` shows concurrent issues funnel to `appendMovement` → `applyDepletingMovement` with only per-key serialization; `tests/infrastructure/inventory-postgres.test.ts` has an over-issue atomicity test (sequential) but **no concurrent-depletion test** (verified: no `Promise.all`/race test in the file).
- **Why it matters:** the ledger is the stock truth; negative balances break FEFO/expiry accounting and any downstream billing/consumption logic. The defect needs concurrency to trigger, but the suite claims race-freedom ("race-free in-memory depletion" — true only because JS is single-threaded).
- **Recommended fix:** serialize per-lot depletion (e.g., `SELECT … FOR UPDATE` on the lot row inside a transaction before the coverage check, or a lot-scoped advisory xact lock), correct the comment, and add a concurrent distinct-key depletion test asserting exactly-one-winner / never-negative.

### SEC-01 — Migration 017 reintroduced the RLS-01 fail-open pattern (Steps 17/20/32)

- **Severity:** MEDIUM (latent) · **Blocks completion:** NO
- **Files:** `db/migrations/017_integration_schema.sql:90–107`
- **Problem:** `pol_external_systems_facility` and `pol_order_external_references_facility` are permissive policies with `sdis.current_facility_id() IS NULL OR …`. Since `current_facility_id()` returns NULL when the GUC is unset (`006`: `NULLIF(current_setting(…), '')`), an `sdis_app` session **without** a facility GUC satisfies the facility policy; combined OR with the tenant policy, rows become visible. There is no RESTRICTIVE policy and no `FORCE` on these tables — the exact defect class migration 014 fixed for older tables.
- **Reachability analysis (why not HIGH):** production paths always stamp both GUCs (`server.ts:192–201` wraps every authenticated route; `Database.query/transaction` stamp only when a scope exists). Unscoped paths run as the pool role = table owner, which bypasses RLS regardless (documented BASELINE-05 residual). `withTenantContext` (the only partial-GUC API) has **zero production callers**. So the fail-open is currently unreachable — but any future `sdis_app`-without-facility path silently exposes all integration rows.
- **Recommended fix:** replace the `IS NULL OR` branches with strict equality (fail-closed), add RESTRICTIVE policies mirroring 014, add `FORCE`, and extend the restrictive-policy gate test to post-014 tables (see TEST-01).

### SEC-02 — `patient_principal_bindings` has no RLS and no policies (Step 22)

- **Severity:** MEDIUM (defense-in-depth) · **Blocks completion:** NO
- **File:** `db/migrations/019_patient_access.sql:43–55` (table + index + `GRANT SELECT, INSERT, UPDATE` — no `ENABLE ROW LEVEL SECURITY`, no policies)
- **Problem:** the table binding patient principals to canonical patient identities is visible org-wide to `sdis_app`, and writable (INSERT/UPDATE). Current code only point-lookups by the session's own `userId` (`repositories.ts:1003–1005`) and has no HTTP write path (bindings are seed/ops-created), so this is not directly exploitable today — but any future list-query, binding-management endpoint, or compromised app-role session exposes every patient↔principal mapping.
- **Recommended fix:** ENABLE + FORCE RLS with org/facility-via-patient policies (or document why the table is exempt), and extend TEST-01's table list.

### SEC-03 — `idempotency_keys`: no RLS, DELETE grant, full-DTO memoized values (Steps 8/33)

- **Severity:** MEDIUM · **Blocks completion:** NO (intent documented in `DATABASE.md`)
- **Files:** `db/migrations/007_idempotency_table.sql` (no RLS; `GRANT … DELETE`); `src/app/idempotency.ts:189–198` (stored `value` is the full operation result DTO)
- **Problem:** keys are facility-scoped by construction, but enforcement is by key secrecy, not by the database. Keys are **client-chosen** (`Idempotency-Key` header — often guessable/sequential), and the memoized value is the complete result DTO. Any `sdis_app` session that guesses another facility's key can read its DTOs; any session can DELETE keys to force duplicate execution (defeating exactly the protection idempotency exists for).
- **Recommended fix:** add RLS (facility derived from key prefix is awkward — prefer a `facility_id` column + policy), drop the DELETE grant (expiry cleanup can run as owner), or minimize memoized values. At minimum, correct the risk statement in `DATABASE.md` to name DTO readability and key-deletion.

### AUD-02 — Clinical acts gated by the semantically wrong permission (Steps 28/25/27)

- **Severity:** MEDIUM · **Blocks completion:** NO (tier-correct today)
- **Files:** `order-service.ts:257` (VERIFIED requires `SETUP_MANAGE`); `report-service.ts:250` (amend requires `SETUP_MANAGE`); `quality-service.ts:123,201` (QC record/release); `worklist-service.ts` `VIEW_PERMISSIONS` (`verification`/`exception` views)
- **Problem:** high-integrity clinical acts (verify diagnostic content, amend a finalized report, record/release QC) require the **setup/config administration** permission. Today both are manager-tier-only so nobody is wrongly allowed or denied — but the mapping is semantically wrong: it grants setup admins clinical authority by name, and any future role split (clinical vs admin managers) silently breaks either clinical workflow or config administration. The code comments acknowledge the tier ("same tier that may create/verify") without acknowledging the misnomer.
- **Recommended fix:** introduce `RESULT_VERIFY` / reuse clinical permissions for clinical acts (keeping manager tier), reserving `SETUP_MANAGE` for configuration; update RBAC.md matrix + tests.

### AUTH-01 — `INTEGRATION_MANAGE` is defined but never enforced (Step 20)

- **Severity:** MEDIUM · **Blocks completion:** NO
- **Files:** `src/app/authz/rbac.ts:56,127` (defined, manager-assigned); zero `assertPermission(…, INTEGRATION_MANAGE)` in `src`; `PostgresExternalSystemRegistry.register` (`repositories.ts:1167`) has no RBAC and no HTTP route (ops/seed-only today)

- **Recommended fix:** gate `register` (and any future disable path) on `INTEGRATION_MANAGE`, or remove the permission and document registration as an ops-only procedure.
